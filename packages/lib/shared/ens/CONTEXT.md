# ens

Addresses are the Sepolia ENSv2 deployment that the canonical Universal Resolver proxy (`0xeEeE…EeEe`) reads: `ROOT_REGISTRY()` returns `0xb458…c43f`, and that root's `getSubregistry("eth")` is `0xd4eb…a8b4` (asserted by `tests/deployment.live.test.ts`). Source commit `07e55a05`. Sepolia also holds an earlier parallel ENSv2 deployment (root `0x9703…51a9ce`, ETHRegistry `0x657e…e09e`, VerifiableFactory `0x9e72…841c`) that some address lists still show; the Universal Resolver does not read it, so names registered there do not resolve. `deployment.ts` reads the root from the Universal Resolver at the pinned block and refuses to continue if it differs from `addresses.ts`. Mainnet runs a different commit (`4f47cbcc`) and different addresses; nothing here targets mainnet. The resolution reference names `ur.integration-tests.eth` and `test.offchaindemo.eth` are kept up to date on mainnet only (on Sepolia the first still answers `0x1111…` through any client), so `tests/deployment.live.test.ts` resolves them through this client against a mainnet RPC: `0x2222…` and a CCIP-Read answer.

`abi.generated.ts` is generated by `bun demo/scripts/genAbi.ts` (`CONTRACTS_V2_DIR=<checkout of ensdomains/contracts-v2>`) from the deployment artifacts in `contracts/deployments/sepolia/*.json` at commit `07e55a05` (the exact ABIs of the deployed addresses, which match `addresses.ts`). Never regenerate it from `main`. `abi.ts` re-exports them and adds the ENSIP read profiles (`text`, `addr`, `contenthash`) used to encode `resolve()` calls. `roles.ts` is transcribed from `RegistryRolesLib.sol`, `PermissionedResolverLib.sol` and `EACBaseRolesLib.sol`. `demo/scripts/abiCheck.ts` calls the view functions against live Sepolia.

Known quirks of the deployed contracts that the checker depends on:

- `PermissionedResolver` has no `text`/`addr`/`contenthash` functions. It is an extended resolver: read with `resolve(dnsName, encodedProfileCall)` (see `resolve.ts`) or through the Universal Resolver. Setters take the DNS-encoded name, not a node. Records are keyed by node; an unknown node falls back to the record linked at node `0x0` (a default record), so a resolver answering for a name proves nothing by itself.
- `UniversalResolver.findResolver` works through the proxy; `findRegistries` and `findOwner` revert. A returned `offset` other than 0 means the resolver was inherited from a parent, i.e. the name itself has no resolver (unregistered, expired, pulled or under a cut key). It can also return resolver `0x0` at offset 0 (it does for `eth`), so check the resolver too.
- `register` reverts with `LabelAlreadyRegistered` on a live label and `LabelAlreadyReserved` when overwriting a reservation with another reservation. Registering a reserved label needs `ROLE_REGISTER_RESERVED` and adds `ROLE_WAS_RESERVED` to the new owner's token roles. `register` with a non-zero registry does emit `SubregistryUpdated` (and `ResolverUpdated`) in the same transaction.
- `unregister` needs `ROLE_UNREGISTER` on the token or the root resource, sets expiry to now, burns the token and bumps the token and EAC versions. Every getter then returns zero, and the next `register` needs only `ROLE_REGISTRAR`.
- Release resolvers grant root only `ROLE_SET_ADDRESS|ROLE_SET_TEXT|ROLE_SET_CONTENTHASH`, without the `_ADMIN` bits, so root cannot grant setter roles to anyone (`grantRootRoles` reverts `EACCannotGrantRoles`). A resolver whose init granted any `_ADMIN` or `ROLE_UPGRADE` bit can be rewritten and cleaned up afterwards; only the logs show it.
- Token ids change on every register and every role grant/revoke on the token (`TokenRegenerated`); key by labelhash, read the current id with `getTokenId(labelId)`.
- Resolver setter roles are scoped per record key (`resource(key)`, `resource(coinType)`); `setContenthash` checks root roles only. `grantRoles` on the resolver always reverts; setter roles are granted with `grantSetterRoles` or `grantRootRoles`.
- `VerifiableFactory.verifyContract(proxy)` returns the implementation address. On a non-proxy it reverts with `VerificationFailed(address)` (`0x4c87e2b6`, confirmed live); treat any revert as "not a factory proxy". VF appends a per-proxy salt to the runtime code, so proxies cannot be recognised by code hash.
- Anvil's default accounts have code on Sepolia (7702 delegations) and cannot receive ERC-1155 tokens, so registration to them reverts with `ERC1155InvalidReceiver`. The demo uses derived keys.

## Spikes (Anvil fork of Sepolia block 12076000, `bun test` in `packages/demo/tests/spikes.test.ts`)

1. Roles: PASS. CI key `register` ok. CI `unregister` reverts `EACUnauthorizedAccountRoles`; CI overwrite of a live label reverts `LabelAlreadyRegistered`; CI register of a reserved label reverts `EACUnauthorizedAccountRoles`; sec `register` reverts `EACUnauthorizedAccountRoles`; sec `unregister` ok, and a CI re-register in the window before root reserves succeeds (expected); sec can clear a reservation; root promotion of a reserved label carries `ROLE_WAS_RESERVED`. Pull + reserve held as one transaction: root is a 1-of-1 Safe, and the pull is one Safe transaction through the canonical `MultiSendCallOnly`; the receipt carries both `LabelUnregistered` and both `LabelReserved` logs.
2. `findResolver` offset: PASS. Offset 0 for a live release and its forward name; offset != 0 for both names after a pull, and for every release under a key after the key is cut.
